## 4. Findings

Severity follows docs/reviews/FINDINGS.md: HIGH blocks the slice, MEDIUM must be fixed before submission, LOW is fixed when cheap or disclosed.

### F-B3-01 MEDIUM, decision needed (Yoann): a payment that arrives for an ineligible broker is not journaled, and a suspense account is required

Trigger: a Checkout Session was created while the broker was approved, the status regressed before `payment_intent.succeeded` arrived (a new failed or pending row from a re-read or a webhook), or the broker was never approved on a database where the payment was injected. `recordSuccessfulPayment` (`lib/payments/collection.ts`) then appends a `succeeded` status with `binding_refused_reason` and posts nothing.

Consequence: Stripe holds cash that the ledger does not show, for as long as the broker stays ineligible, which can be for ever if the verification ends `failed`. This contradicts the brief's non-negotiable 2 and the first paragraph of AF-03 ("every external money event must be reflected in the journal"). There is no detector today except the policy page: reconciliation (B10) is not built, and the non-zero clearing list cannot show it because no clearing account was touched. There is also no ledger path to give the money back: a refund of premium that was never journaled has nothing to debit.

Assessment requested by the coordinator: yes, a suspense account is required to satisfy the letter of the requirement and to make the failed-broker case resolvable. Smallest shape: one credit account `unapplied_customer_funds` in `accounts`; on a refused binding, one entry `cash_received_unapplied` (Dr `cash_stripe` / Cr `unapplied_customer_funds`, source `money_operation`, the operation id) posted in the same transaction as the `succeeded` status; on the staff binding, the four issuance entries with `premium_collected` replaced by `unapplied_funds_applied` (Dr `unapplied_customer_funds` / Cr `premium_receivable`); on a broker that ends `failed`, a `stripe_refund` operation (maker-checker above $1,000) with Dr `unapplied_customer_funds` / Cr `refund_payable`. The account joins the non-zero clearing list with its age. Alternative, acceptable only with Yoann's explicit decision and a README limitation: keep the current behaviour, and document the operator procedure. Not a HIGH: the path has not occurred on the trial ledger (no `binding_refused_reason` row exists), the money is recorded on the operation, and the case is visible in red. Register it in FINDINGS.md; until decided, the AGENTS.md feature-completion gate for B3 stays open on this item.

### F-B3-02 MEDIUM: the comments promise a same-key retry after a lost answer that the code cannot perform

Trigger: `startBrokerVerification` fails after Stripe accepted the request (timeout, dropped connection). The catch in `submitBrokerKyb` appends `failed` with the connection error; the broker resubmits; `countBrokerKybSubmissions + 1` derives a NEW key (`broker-kyb:<broker>:2`) and Stripe creates a SECOND connected account. Migration 0006 ("a submission retried after a lost answer reuses it") and `lib/broker/kyb-onboarding.ts` ("the retry reuses the same idempotency key") describe a recovery path that does not exist: no function re-sends a submission with its stored key, and it could not be written as designed, because the full EIN is not stored (by design) and Stripe's idempotency requires identical parameters.

Consequence: sandbox hygiene only (an orphan connected account whose `account.updated` is ignored with the reason "belongs to no broker of ours"), but an AF-06 hazard: the panel pointing at those lines would get a description that the code contradicts. Correction: rewrite both comments to say what happens (a lost answer is recorded as failed; a resubmission creates a new account under a new key; the previous account is orphaned at Stripe and ignored), or implement a bounded resend that asks the broker to re-enter the EIN and reuses the stored key when the last submission has no outcome. The comment fix is the cheap and honest one.

### F-B3-03 MEDIUM: the deployed application cannot show pending or failed today, and no KYB submission has gone through the deployed URL

Facts: the trial database holds one broker, already approved; `submitBrokerKyb` refuses a new submission while the latest status is approved; the failed path was proven on corgi_test only; all three submissions recorded on the trial database were made from the delegate's local server (the ToS acceptance IP that Stripe holds for the demo account is `::1`). The brief's Track 1 slot requires pending and failed to be shown, and AF-02 requires real requests from the deployed application where required.

Correction (coordinator, before the debrief and the evidence pack): add a second demo broker with its own broker user to the trial database by an owner insert (the seed refuses a non-empty database), keep it unsubmitted, and at the debrief submit it live on the deployed URL (pending for the first minutes, then approved through the re-read, or failed with EIN 111111111). Record that deployed-app submission as the KYB evidence, as F-B2-04 did for payments. A second broker also gives `/ops/brokers` its first multi-row state.

### F-B3-04 LOW: an approval recorded inside the settling window is held for ever, and the broker is then locked out

Trigger: an approval row appended less than 120 s after the submission row. The mapping prevents it when clocks agree (an account is created about 4 s after the submission row, and the mapping refuses approval for 120 s after Stripe's `created`), so it needs about 5 s of skew between Stripe's clock and the Neon or Vercel clocks. If it happens: `reportedKybStatus` reports pending for ever, a re-read appends nothing ("still approved"), and a resubmission is refused as "already verified" because that check reads the recorded status. No escape in the UI. Cheap fix that matches Yoann's wording ("held at pending for at least 2 minutes"): make the hold time-relative, reporting approved once `now − submission ≥ 120 s`, with `now` passed as an argument so the function stays pure and testable.

### F-B3-05 LOW: the double-click guarantee is narrower than the comments say

The unique index on `provider_idempotency_key` only stops two requests that computed the same attempt number. A second click that arrives after the first insert committed (tens of milliseconds) computes attempt 2 and creates a second connected account. Sandbox hygiene only, and both accounts carry the same data. Cheap mitigation: take `pg_advisory_xact_lock(hashtext(brokerId))` around the latest-event check, the count and the insert, and refuse a submission while the latest submission has no status row referencing it and is younger than a few minutes; or disable the button client-side and state the limitation in the comment. Related: an `assertStripeSandbox` failure after the insert leaves a submission with no status row and answers a 500 rather than a recorded failure.

### F-B3-06 LOW: README is behind the Connect endpoint and the new check

README still says to register one endpoint with `account.updated` among its events and one `STRIPE_WEBHOOK_SECRET`; a clean-clone deployment following it would never receive connected-account events. Add the second endpoint ("listen to events on connected accounts", `account.updated` only, same URL) and `STRIPE_CONNECT_WEBHOOK_SECRET`, and add `npm run check:kyb-replay` to the checks list. The inventory row's evidence pointer to STATUS.md is now satisfied by the 12:41Z entry.

### F-B3-07 LOW: a paid policy whose binding was refused reads `awaiting_payment` in lists

`derivePolicyStatus` has no state for "paid, not bound", so the broker's policy list shows `awaiting_payment` while the customer's money is at Stripe, and once the broker becomes approved the owning broker is offered "Continue the payment at Stripe" on an already-paid policy (the session is complete, so Stripe takes no second payment; the button is only misleading). A derived `paid_not_bound` status, or a note in the list, would make the case visible outside the policy page. Also cosmetic: a replay of `payment_intent.succeeded` on an already-bound policy after a status regression is answered "paid, binding refused" in the inbox reason although nothing changed; checking `already_posted` before eligibility on replays would give the truthful reason.

### F-B3-08 LOW: the "not a dedicated KYB vendor" disclosure is in README but not on the screens

ARCHITECTURE.md section 4 says README and UI disclose that both live slots run on Stripe and that Stripe is not a dedicated KYB vendor; DECISIONS.md 08:55Z requires README, the inventory and the debrief. The screens say "Stripe Connect in test mode" but not the vendor limitation. One sentence on `/broker/kyb` and `/ops/brokers` closes the gap with the design text.

### F-B3-09 LOW, observation outside this scope: two migrations numbered 0007 on the trial database

`schema_migrations` on the trial database lists `0007_claims_and_approvals.sql` (applied 12:38Z from the B7 branch) next to `0007_policy_current_voided_status.sql`; the repository at `09e71e5` has only the latter. The fresh-database check passed for the repository's seven files. Because the runner keys on the file name, the B7 file must keep its name when merged; the coordinator should note the collision so nobody "fixes" it by renaming an applied file.
