## 4. Money path, as verified

1. Broker POSTs the quote form. `app/api/policies/route.ts` reads the session, requires role `broker`, parses dollar amounts without floats (`parseUsdAmountToCents`), and calls `createPolicyDraft`, which prices the draft with the rate in force on the effective date and writes `policies`, one `quoted` event carrying the terms, and the cache, in one transaction. No money moves.
2. Broker POSTs Pay. The route requires role `broker`; `startCheckout` re-reads the policy, refuses another broker's policy, refuses an already issued policy, refuses unless the latest KYB event is `approved`, then commits the operation with `requested` (amount = quoted total), checks Stripe answers in test mode, creates the session with the intent-derived idempotency key, and appends `provider_accepted` with the hosted URL. A second click returns the stored URL. A Stripe error is appended as `failed` and shown; the same request can be retried with the same key.
3. Stripe delivers `payment_intent.succeeded` to the deployed URL. The route verifies the signature on the raw body, refuses live mode, stores the event once, takes the lease, reads `metadata.operation_id` (UUID-checked), and calls `recordSuccessfulPayment`. The amount is compared with the operation's amount; then, in one transaction: four entries keyed on the operation, the `succeeded` event, the `issued` policy event, the cache. A unique violation is answered as already posted. `checkout.session.completed` appends a lifecycle note and posts nothing; `payment_intent.payment_failed` appends `failed` and posts nothing.
4. Effective dates: `premium_written` and `tax_and_fee_billed` carry the term start; `premium_collected` and `commission_earned` carry the UTC day of `paymentIntent.created`. Observed on CGP-01062 (paid 2026-09-08 for a term starting 2026-10-01): as of today `premium_receivable` is a credit balance of 355684 and `unearned_premium` is 0 until October 1; the sum is right and the reading ("the customer's credit balance until coverage starts") is documented in `policy-entries.ts`. See F-B2-12.

## 5. Findings

### HIGH

**F-B2-01 The deployed system shows a policy as paid and bound on a locally fabricated payment confirmation.** Trigger and evidence (trial database, read-only): policy `CGP-01061` (id `de2fb99f-...`) has an `issued` event recorded at 09:58:32Z, four journal entries (268640 cents of debits) with the description "collected at Stripe", and a `succeeded` operation event whose `provider_ref` is `pi_local_fafe3cc4`. The inbox rows that caused it are `evt_local_fafe3cc4_payment_intent_succeeded` and `..._second-event`, built by `scripts/post-local-webhook.ts`, signed with the delegate's local webhook secret and posted to a local server whose `DATABASE_URL_APP` pointed at the shared trial database (the delegate's notes, section 9, confirm the run). The real Checkout Session of that operation (`cs_test_b1BblgFhUn...`) was never paid: Stripe has no `payment_intent.succeeded` for it, and the only real payment on the account for this build is `pi_3UDM4KK6R3v50tIy0F5xaBbu` for CGP-01062. The deployed broker workspace lists CGP-01061 as `bound` next to the genuinely paid CGP-01062 with no distinction; the ledger's `cash_stripe` (481004) exceeds what Stripe holds (355684). Consequence: AF-02 in its exact wording ("a simulated integration presented as live"; "locally fabricated responses do not count") applies the moment the deployed URL is handed over with this row unlabelled, and the trial ledger now carries a permanent local-only break that reconciliation (B10) will report. Nothing can be deleted (AF-03). Location: data in the trial database; the tooling that made it possible is `scripts/post-local-webhook.ts` (refuses non-localhost targets but not a local server wired to the trial database). Required correction, needs Yoann's decision on the shape: (a) correct the ledger the AF-03 way: reversal entries for the four (using `reverses_entry_id`, description stating that the confirmation came from a local test event and no money moved at Stripe) plus a `cancelled` policy event with the same reason, and disclose the episode in README and the evidence pack; or (b) leave the rows, label them in the interface (a note on any policy whose `succeeded` event has a `pi_local_` reference) and in README, and let reconciliation report the break as a known, explained item. In both cases the evidence pack must never cite CGP-01061, and local end-to-end runs must be confined to `corgi_test`: make `post-local-webhook.ts` refuse to run unless the server's database is `corgi_test` (the route could return that name on `/api/health`), or make the route refuse `evt_local_`/`pi_local_` identifiers unless an explicit local flag is set that Vercel never sets.

### MEDIUM

**F-B2-02 A delivery that arrives while a lease is in flight is acknowledged, so a lease holder that dies before commit loses the event.** Trigger: `payment_intent.succeeded` is stored and leased; the function is killed (timeout, deploy, out of memory) before `recordSuccessfulPayment`'s transaction commits; Stripe retries the same event within five minutes; `takeProcessingLease` finds `processing` with a fresh `updated_at`, returns no lease, and the route answers 200 `duplicate: true` (`app/api/webhooks/stripe/route.ts`, the `if (!lease)` branch). Stripe records the event as delivered and stops. Consequence: a customer has paid, no entry exists, the policy stays `awaiting_payment`, the row stays `processing` for ever, and nothing in the application lists it: the failed and stuck events view with replay required by design section 5 (F-01 correction items 4 and 6, and F-B1-11 "must land in B2") is not in this slice. The design text says 500 while processing is not done; the code says 200. No double post is possible (unique index), so the money is never counted twice; it is the lost-event half that is open. Required correction: when no lease is obtained, read the row's status and answer 200 only for `done` or `ignored`; answer 503 for `pending`, `failed` or an unexpired `processing` so Stripe retries and the retry either finds `done` or re-leases after expiry; add the stuck and ignored events listing with an authorized replay (a script is enough for the checkpoint, a staff screen for B13); document in the route that `done` is set after the posting transaction and why that is safe (the unique index makes the re-lease idempotent).

**F-B2-03 A draft older than 24 hours can never be paid.** Trigger: Stripe Checkout Sessions expire after 24 hours; `checkout.session.expired` is stored and `ignored`; `startCheckout` always returns the first stored `checkout_url` for the operation. Consequence: the broker is sent to an expired Stripe page with no way to open a new session; the policy stays `awaiting_payment`; the only exit is a new draft, which leaves an orphan operation. Stripe's idempotency key retention is also 24 hours, so a same-key resend after that would create a second session that the operation would not know. Location: `lib/payments/checkout.ts` (`existingCheckoutOperation`), `route.ts` (no handler). Required correction: handle `checkout.session.expired` by appending a terminal operation event (for example `failed` with reason `session_expired`), and let `startCheckout` create a new operation with a new intent key (`policy-checkout:<policy id>:<attempt>`) when the latest event of the previous operation is that expiry, so the first operation's history stays intact; or, if Yoann prefers to keep one operation per policy in v0, show "payment page expired, create a new draft" and record the limitation in README. Either way the status shown must stop saying `awaiting_payment` for an expired session.

**F-B2-04 The live proof covers the webhook leg from the deployed system, not the outbound leg.** Evidence: the Checkout Session paid at 10:16Z (`cs_test_b1LAjB...`, operation `ddede650-...`) was created at 10:00:09Z by the delegate's local server (its return URLs point to `localhost:3100`, per the notes), and the payment was then made on that hosted page; the resulting `payment_intent.succeeded` and `checkout.session.completed` were received and processed by the deployed URL. Consequence: non-negotiable 3 asks for "real API calls and real webhooks received by the deployed system"; the API call that created this session did not come from the deployed application, and no Checkout Session has yet been created from it. Required correction: create a fresh draft on the deployed URL, pay it with a test card, and record the session id, the event ids and the four entries; that run becomes the evidence for both legs. Quick, and it doubles as the demo policy that has no local history.

### LOW

**F-B2-05 Lifecycle regressions are recorded, not ignored.** Observed on CGP-01062: `checkout.session.completed` arrived 200 ms after `payment_intent.succeeded` and was appended as `provider_accepted` (event #113) after `succeeded` (#112), so "current status = latest event" now says `provider_accepted` for a paid operation; the policy page shows "last status: provider_accepted". A `payment_intent.payment_failed` arriving after success would likewise append `failed`. The policy status is safe (an `issued` event wins), but the payment section misleads and a B10 comparison by latest status would misclassify. Correction: a dedicated status value for session completion (one line in the CHECK plus a migration) or skip appending a lower lifecycle state when `succeeded` already exists, as ARCHITECTURE section 5 promises.

**F-B2-06 Amount mismatch and unknown operation are terminal `ignored` outcomes with no view, and currency is not compared.** A real Stripe payment for a different amount is money Stripe collected that the ledger never shows; marking it `ignored` rather than `failed` is right (a retry cannot change the amount) but it must be visible: today only a database query finds it. `recordSuccessfulPayment` also does not compare `paymentIntent.currency` with `usd` (one line). Correction: include `ignored` rows in the listing of F-B2-02, disclose in README that partial captures are refused, compare the currency, and have B10 classify such payments as provider-only.

**F-B2-07 The cash date comes from `paymentIntent.created`, not from the success.** With API version `2026-08-26.dahlia` the PaymentIntent is created at confirmation (observed: 1 second before the event on the real payment, and the session's `payment_intent` was null at creation), so the date is right in the common case. A card declined then retried on the same PaymentIntent, or a confirmation straddling UTC midnight, would date `premium_collected` and `commission_earned` a day early, which moves them across a statement month in B9. Correction: use `event.created` (or the charge's `created`) for `paidOn`, and say in the code which timestamp "the day the money moved" is.

**F-B2-08 Two concurrent first clicks on Pay give one broker a 500.** Both requests see no operation; the second `createCheckoutOperation` hits the unique `idempotency_key` and the unique violation propagates as a generic error (no money effect: Stripe is not called by the loser). Two concurrent retries of an operation without URL would send the same key to Stripe concurrently, and Stripe's 409 idempotency conflict would be appended as `failed` (see F-B2-05). Correction: catch the unique violation and re-read the existing operation; treat a Stripe idempotency conflict as "retry the read" rather than a failure.

**F-B2-09 KYB is checked when the session is created, not when the policy binds.** A broker whose latest KYB event turns `failed` during the session's lifetime still binds on the webhook. Acceptable in B2 (the money has moved and refusing to bind would need the B5 refund path), but B3 should decide and document the rule: re-check at posting and, if not approved, journal the cash as received without issuing and route it to a refund, or accept the window explicitly.

**F-B2-10 Hygiene and disclosures.** Three worktrees under `.claude/worktrees/` each hold a copy of `.env.local` (one with the delegate's modified local webhook secret) and `.next` caches; the working-tree secret scan flags them (39 items), all ignored and untracked; remove the worktrees now that B2 is merged. The trial inbox holds three B1a rows whose `payload` is a jsonb string (queries over historical payloads must tolerate it), two `evt_replaytest_*` and four `evt_local_*` synthetic events; all to be disclosed in README (B6) with F-B2-01.

**F-B2-11 Explicitness items.** Assert `terms.totalChargeCents === operation.amountCents` in `recordSuccessfulPayment` before posting (today both come from the same quote; B4 will add terms-carrying events). `policies.created_at`, `brokers.created_at`, `customers.created_at` are client-settable (ordering only; no money). F-B1-10 (column-level UPDATE grant on `webhook_processing`) is still open and 0002 did not take it. A Stripe error at session creation is appended as `failed` and displayed as `payment_failed`, which reads as a card decline. `route.ts` should state that `done` is written after the posting transaction and why that is safe (F-B1-12).

**F-B2-12 Reading of the negative receivable before the effective date.** Premium and tax dated at term start, cash and commission on the payment day: between the two dates an as-of balance sheet shows `premium_receivable` as a credit balance instead of an "advance premium" liability, and `unearned_premium` at zero. Arithmetically consistent, documented in `policy-entries.ts`, and consistent with commission on collected premium. For B9 and the B13 walkthrough, either name it (an `advance_premium` account credited at collection and cleared at term start) or write the reading in README so the answer at the debrief is the written rule. Not a defect.

Other items evaluated and accepted: the `quoted` event (an immutable price the charge cannot drift from, one per policy); the $25 fee labelled as an assumption in code, on the quote form and on the policy page; `checkout.session.completed` posting nothing; `scripts/migrate.ts` loading `.env.local` unconditionally (verified with a probe: a variable already in the environment wins over the file, so `DATABASE_URL=<x> npm run migrate` targets `<x>`); `next.config.ts` `agentRules: false` (keeps Next.js from appending to `AGENTS.md`, harmless).
