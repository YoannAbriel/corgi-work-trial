## 4. Money path, as verified

1. The owning broker (or `staff_ops`) opens `/policies/{id}/cancel?effectiveAt=...`. The page calls `planCancellation`, which checks the actor, the method, that the policy is issued and not cancelled, that the date is a real calendar day inside the term, computes the breakdown with `cancellationBreakdown`, subtracts premium already recognised as earned (always zero today), allocates the refund over the collected Stripe payments newest first, and returns the plan with a policy version. Nothing is written.
2. Confirm POSTs the date, the method and the version. `recordCancellation` recomputes the plan, refuses a changed version, then in one transaction writes the `cancelled` policy event (every figure in its payload), the `premium_earned_to_date` entry (skipped on day zero), and per Stripe payment a `stripe_refund` operation in `requested`, its `refund_allocations` row and its `refund_requested` entry, then refreshes the cache. The partial unique index makes a second `cancelled` event impossible.
3. After the commit, `issueRefundsAtStripe` checks the sandbox, lists the PaymentIntent's refunds for one carrying this operation id, and only then calls `refunds.create` with the stable key and metadata. The answer is appended as `provider_accepted` with the refund id; a provider error is appended as `failed` and shown, with `refund_payable` still open.
4. Stripe delivers `refund.created`, `refund.updated` and `charge.refunded`. The route verifies, stores once, leases, finds the operation by metadata (or by refund id, or by an unambiguous open allocation on the PaymentIntent), records the refund id if not yet known, and on status `succeeded` posts `refund_completed` and `commission_clawback` with the `succeeded` lifecycle event in one transaction. A second delivery, or a second event describing the same refund, hits the journal's unique key and is answered as already posted. On `failed` or `canceled` nothing is posted.
5. Dates: `premium_earned_to_date` and `refund_requested` carry the cancellation effective date; `refund_completed` and `commission_clawback` carry the UTC day of the refund's `created` timestamp, like `premium_collected` at issuance.

Observed end to end on the trial database for CGP-01062 (section 7): unearned premium emptied (345075 credited at issuance, 28362 + 316713 debited), `refund_payable` opened at 324156 and closed at 324156, `cash_stripe` for the policy 31528 = 355684 minus 324156, `premium_tax_payable` for the policy 666 = 8109 minus 7443 (the tax on the 28362 earned is 666.5), commission payable 4255 = 51761 minus 47506, global debits = credits = 2537535 over 45 lines.

**F-B5-01 The live refund of $3,241.56 exceeded the build's own $1,000 money-out threshold with no human approver, and nothing in the code gates a `stripe_refund` today.** Facts: DECISIONS.md (08:04:03Z) sets money-out above $1,000 as needing a distinct human approver; slice B7 (approval queue) does not exist; `cancelPolicy` calls `issueRefundsAtStripe` immediately after the commit for any amount. Consequence: the general non-negotiable 6 is not met by the integrated system yet, and any further live cancellation of a real policy above the threshold before B7 repeats the gap (CGP-01274's refund on any date this month would also exceed it). Required correction: B7 must route `stripe_refund` operations above the threshold through `approval_requests` between `recordCancellation` and `issueRefundsAtStripe` (the seam already exists), re-check the approval and the intent hash at execution, and the B7 review must confirm it. Until then, no further above-threshold live cancellation without Yoann's explicit acceptance, and the evidence pack must state that this refund was executed before the gate existed. Needs Yoann: acknowledge the disclosure wording.

**F-B5-02 A staff re-issue can send a second Stripe refund when the first create actually succeeded at Stripe.** Trigger: `refunds.create` times out or errors after Stripe accepted it; `issueOneRefundAtStripe` appends `failed` (stage `create_refund`); before the `refund.created` webhook arrives (or if delivery is delayed), `staff_ops` clicks "Re-issue this refund". `createReissuedRefundOperation` only checks `state === "failed"`, creates operation 2 with key `...:2`, and `recoverPendingRefund` looks for a refund carrying operation 2's id, which cannot exist, so `refunds.create` is called again. Consequence: two refunds at Stripe for one liability; the ledger would post one completion (the second webhook is refused on the amount or hits the unique key) and the customer is paid twice. Bounded by Stripe's own cap (a refund cannot exceed the charge's remaining balance, so a full refund cannot be doubled; a partial one can) and by the webhook usually arriving within a second. Location: `lib/payments/refunds.ts` (`createReissuedRefundOperation`, `recoverPendingRefund`), `app/api/policies/[policyId]/refunds/[operationId]/reissue/route.ts`. AGENTS.md: "Never blindly retry a financial side effect with a new key." Required correction: distinguish the two failure kinds already recorded in the payload (`stage: create_refund` versus `stage: refund_lifecycle`): a create-stage failure is retried on the same operation with the same key (call `issueRefundsAtStripe([operationId])` again; the recovery listing then finds a refund created under that same operation id), and only a lifecycle failure reported by Stripe (`refund.failed`, `canceled`) may become a new operation; additionally, before creating any re-issued operation, list the PaymentIntent's refunds and refuse if one carrying the failed operation's id is not itself `failed` or `canceled`. Add the case to `check:refund-replay`.

**F-B5-03 A refund operation stuck in `requested` has no recovery entry point.** Trigger: the process dies after `recordCancellation` commits and before `refunds.create` returns (or before the `provider_accepted` insert when Stripe was never reached). The operation stays `requested` with no refund id; the policy page shows "requested $X, not created yet" for ever; `reissueRefund` refuses anything that is not `failed`; the `recover-operations` job promised by ARCHITECTURE sections 4 and 7 does not exist (no `app/api/jobs` route). Consequence: the liability stays open and visible, which is the honest state, but only a code change can resume it. Money is safe (nothing was sent). Required correction: a `staff_ops` action "send to Stripe again" for a `requested` operation without refund id, which calls `issueRefundsAtStripe` for that operation (same key, recovery listing first, so it is safe to click twice), or the recovery job of the design; disclose in README until then.

**F-B5-04 The outbound refund API call has not yet been made by the deployed application.** Evidence: the refund `re_3UDM4KK6R3v50tIy0scSGaps` was created by the delegate's worktree server against the trial database and the real Stripe sandbox (notes, section 5); the deployed URL received the resulting webhooks (three at revision B2, stored and marked `ignored` with "no handler for refund.*", which is disclosed, not hidden, and one at `e120f69` that posted). The same caveat as F-B2-04 applies to this slice: non-negotiable 3 wants real API calls and real webhooks from the deployed system. Required correction: one cancellation confirmed on the deployed URL, with its refund id, event ids and the four entries recorded as the evidence for both legs. Tension with F-B5-01: CGP-01274 refunds above $1,000 on any date this month, so either Yoann accepts one more above-threshold live refund with the disclosure, or a small policy (premium such that the refund stays under $1,000) is issued and cancelled for the proof, or the proof waits for B7. ### LOW

**F-B5-05 Version check and double cancellation.** `expectedPolicyVersion` is compared outside the posting transaction; today the only event that can land in between is a second cancellation, which the partial unique index refuses, so money is safe. But that refusal surfaces as a unique-violation error, not a `CancellationRefused`, so two simultaneous confirmations give one user a 500 instead of "already cancelled" (same class as F-B2-08). When B4 adds endorsements, the version comparison must move inside the transaction with a row lock on `policies` (or a `select ... for update`), otherwise an endorsement landing between the check and the insert would go unnoticed. Catch the unique violation on the `cancelled` insert and answer "already cancelled".

**F-B5-06 The refund's cash date is `refund.created`, not the moment it succeeded.** `handleRefundEvent` passes `utcCalendarDate(refund.created)`; for a card refund that is `succeeded` in its first event this is the same day. A refund that stays `pending` and succeeds days later would date `refund_completed` and `commission_clawback` early and could move them across a statement month (B9). Same class as F-B2-07: use `event.created` of the event that carried `succeeded`, and say so in the code.

**F-B5-07 PaymentIntent fallback can attribute a foreign refund to our operation.** `findRefundOperationId`'s third way matches any refund on the PaymentIntent to our single open allocation. A refund created by a human in the Stripe dashboard on the same payment, for the same amount, would be booked as ours; for a different amount it is refused. Metadata and the stored refund id are the trustworthy paths. Either drop the fallback (store and `ignore` for a human) or document that B10 will report the second Stripe refund as provider-only.
