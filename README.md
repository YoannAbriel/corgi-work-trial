# Corgi work trial, Track 1: policy administration

A commercial liability policy from sale to cancellation, with every dollar collected and refunded in the application's own append-only double-entry ledger. Built in the 48-hour window from September 8, 2026, 07:50 Europe/Zurich. Sandbox providers and synthetic data only; no live keys, no real money, no real people.

Deployed URL: https://corgi-work-trial-iota.vercel.app (health: `/api/health` reports the database and the built revision). Demo credentials are handed over in the submission email; roles: `broker@example.com` (broker, KYB approved), `broker2@example.com` (broker, KYB failed on Stripe's tax-id fixture), `broker3@example.com` (broker, never submitted, for a live pending demonstration), `customer@example.com` (customer of the seeded policies), `customer2@example.com` (customer of CGP-01274 on the deployed app, attached by hand on 2026-09-08 so the endorsement approval can be demonstrated), `ops@example.com` (staff operations, maker), `approver@example.com` (staff approver, checker). All share the demo password from the deployment secret store. The account menu at the foot of the sidebar switches between the six demo accounts without retyping the shared password; it is a demo device restricted by code to those six accounts and is removed before any real deployment. Disclosure (review finding F-LT-05): because of that menu, any demo session can become the approver in one click, so on this demo the maker-checker control rests on the closed list of six accounts; the ledger-side proof is unaffected (the initiator check compares user ids on rows), and a real deployment removes the menu.

## Run it from a clean clone

Prerequisites: Node 20.19 or later, npm, a Postgres database (Neon free tier is what the deployment uses), a Stripe sandbox (test-mode key), gitleaks for the pre-commit hook.

```bash
git clone https://github.com/YoannAbriel/corgi-work-trial.git && cd corgi-work-trial
npm install
cp .env.example .env.local            # fill in: DATABASE_URL (owner), STRIPE_SECRET_KEY (sk_test_), APP secrets
git config core.hooksPath .githooks   # gitleaks runs on every commit
npm run migrate                       # applies db/migrations/*.sql once each, in name order
npm run set-runtime-role-password     # gives the app_runtime role its password (APP_RUNTIME_DB_PASSWORD)
#   then set DATABASE_URL_APP to the app_runtime connection string; the app refuses to start without it
npm run seed                          # seed from zero: refuses if any table it fills already holds a row
npm run dev                           # http://localhost:3000, log in with a demo user and DEMO_PASSWORD
```

Webhooks: register `https://<your deployment>/api/webhooks/stripe` in the Stripe sandbox for `payment_intent.succeeded`, `payment_intent.payment_failed`, `checkout.session.completed`, `checkout.session.expired`, `refund.created`, `refund.updated`, `refund.failed`, `charge.refunded`, `account.updated`; put its signing secret in `STRIPE_WEBHOOK_SECRET`. Locally, `stripe listen --forward-to localhost:3000/api/webhooks/stripe` prints the secret to use instead. Connected-account events need a second endpoint on the same URL created with `connect=true` (listening to `account.updated`); it has its own signing secret, `STRIPE_CONNECT_WEBHOOK_SECRET`, and the route verifies each delivery against either secret.

## MCP surface

`POST /api/mcp` is a streamable HTTP MCP endpoint (JSON-RPC 2.0) authenticated by a per-user API key: `Authorization: Bearer <key>`. A key is created by staff operations on `/ops/mcp-keys` or with `npm run create-mcp-key -- --email=<demo user> --label="<what it is>" --kind=agent|human`; the secret is shown once and only its sha256 is stored. A wrong or revoked key answers 401 with no detail. Every call is recorded in `mcp_calls` (method, tool, a hash of the arguments, outcome), never the payload. There is no rate limiting in this build. An MCP key never expires. Revoking it on /ops/mcp-keys is the only thing that ends it, and a revocation is a new row, never an update. The screen shows each key's call count and the time of its last call, so a key nobody uses is visible, but nothing retires it on its own. A key borrows the visibility of its user: a broker key sees that broker's policies, a staff key sees everything.

Eight tools: six that read (`get_policy_as_of`, `get_broker_statement`, `explain_amount`, `list_my_activity`, `inspect_reference`, `list_reconciliation_breaks`), `run_reconciliation` (appends a comparison run, moves no money) and `request_claim_payment`, which only puts a payment into the human approval queue. Each one declares in `tools/list` whether it reads only, so a client sees the shape of the surface without reading a description.

| Tool | One example |
|---|---|
| `get_policy_as_of` | `{"policyNumber":"CGP-01274","asOf":"2028-06-09"}` gives the policy as it stood on that business date: status, term, premium in force, tax, fee, limits, endorsements applied by then. |
| `get_broker_statement` | `{"brokerId":"me","month":"2028-03"}` gives that published statement: its lines, its five totals, its content hash, its knowledge cutoff, its format version. |
| `explain_amount` | `{"policy":"CGP-01274","figure":"premium_tax","asOf":"2028-03-01"}` gives the fold the policy screen shows under that figure: `floor(120000 x 235 / 10000)` = 2820, the rounding rule by name, and the journal entry ids that prove it. |
| `list_my_activity` | `{}` gives the last 50 calls this key's user made here, newest first: when, which tool, ok or refused, the rule that refused it, the duration, the correlation id. |
| `inspect_reference` | `{"reference":"pi_3RxxxxSTRIPExxxx"}` gives the operational file of that reference: what it resolved to, the policy or claim it belongs to with the terms in force today, the money operation with its lifecycle instants and its terminal status, the provider events that touched it, the journal entries with their lines, what reconciliation last reported about it, and the last 20 requests answered about it. |
| `list_reconciliation_breaks` | `{"source":"stripe"}` gives the open breaks of the latest complete run and the four clearing balances. Staff keys only. |
| `run_reconciliation` | `{"windowDays":7}` runs both comparisons and returns the run ids and counts. It posts no journal entry. |
| `request_claim_payment` | `{"claimNumber":"CLM-00042","amountCents":120000}` creates an approval request. No money moves, ever. |

`explain_amount` accepts a closed list of fifteen figure keys, published in its description and in its `tools/list` annotation with what each one means: the three terms in force (`premium_tax`, `policy_fee`, `total_charge`), the four ledger sums (`collected_at_stripe`, `refunded_from_stripe`, `commission_payable`, `unearned_premium_held`), the prorated `endorsement_delta`, and the seven cancellation figures (`cancellation_written_premium` to `cancellation_commission_clawback`). A key it does not know is refused by naming the list, never by repeating what the caller sent, and that refusal comes from the transport before the tool runs, so a misspelled key never reaches a policy row. Two gates decide the answer, not one, and both live in `lib/mcp/scope.ts` with a unit test each (`lib/mcp/scope.test.ts`): **who may explain at all**, and **which policies that key can name**. A broker key explains its own policies and a staff key explains any of them, all fifteen figures, exactly what those users read on the screen. **A customer key is refused `explain_amount` altogether**, with one sentence that names the rule and never a figure key or a policy number: the customer policy screen prints the terms in force and the endorsement schedule as plain amounts, with no explanation fold, no journal entries and no broker commission, so there is nothing on it for a customer key to explain; the amounts themselves are on `get_policy_as_of`. A per-figure allowlist was tried first and removed: it gated which key a caller could **name** and never what the answer **contained**, and the answer is always the whole fold, so the commission it refused by name came back inside a figure it allowed (review findings F-MCPTOOLS-02 and F-MCPTOOLS-03). The explanation is not a second calculation written for machines: `lib/policy/explain-figure.ts` composes the same functions the policy page composes (`lib/money/explain.ts`), and the answer carries the check the screen makes on every render, `explanationEndsOnTheFigure`, rather than hiding a disagreement. `list_my_activity` reads `activity_log`, which has no column for a request or response body; it does record one sanitised sentence per call in a `message` column, which the tool does not read back. It returns the rows of the user behind the key and of no other, so a user holding two keys sees both keys' calls and nobody else's. Its answer is bounded to 50 rows; its **work** is not, because nothing indexes `actor_user_id`: measured on the disposable database at about a thousand rows it is a sequential scan taking a quarter of a millisecond, and forcing the existing time index instead makes it slower, because reading in time order cannot skip another user's rows. That is accepted at this scale; the plans, the numbers and the one index that would fix it, `(actor_user_id, recorded_at desc)`, are written out in `lib/mcp/tools/my-activity.ts`.

`inspect_reference` (decision 42) is the tool for the reference you actually have during an incident, which is rarely a policy number. It accepts a closed list of eight shapes, published in its description and in its `tools/list` annotation: a Stripe id (`pi_`, `cs_`, `re_`, `acct_`), an application uuid (a money operation, a policy or a claim), a policy number, a claim number, a reconciliation break key, and the correlation id of a request. **An email address is not on that list and no email, customer name or claimant name is ever in the answer**; the activity rows come back without the actor's name and without the sanitised `message` sentence, exactly as `list_my_activity` leaves them out. **An MCP key prefix (`cmk_`) is recognised in order to be refused**, with the reason: reading an API key is on the never-delegated list, because a key names the user whose visibility it borrows. Every list is bounded to 20 rows and the answer carries its own bounds beside them, so an agent never has to guess whether it is holding all of something. A reference that matches nothing answers a "nothing matches" result rather than an error, because "I looked and there is nothing" and "the tool broke" are different findings. It writes nothing: every query behind it is one of the console readers the staff screens already use (`lib/console/read.ts`, `lib/reconciliation/read.ts`), so a figure an agent quotes here is the figure a person reads on `/ops/console`. Two gates decide the answer, both in `lib/mcp/scope.ts` with a unit test each: **a customer key is refused the whole tool** before any read, because the customer screens show no money operation, no webhook event, no journal entry and no reconciliation report; **a broker key opens the references of its own book of business** and is refused anything else with one sentence that names nothing about the reference, not its kind, not its number, not its owner. The provider events and the reconciliation reports are staff keys only, exactly as `list_reconciliation_breaks` is, and a broker key is told which sections were not read rather than shown two empty lists. **A reference that resolves to a broker** (a connected account id, or the correlation id of a request that named one) **opens that broker's whole book and names no policy at all**: the money operations, the journal entries and the requests span every policy of the book, so the answer carries no policy number, no status, no term and no terms in force, and says instead how many policies those lists were drawn from (review finding F-INSPECT-01; before the fix it published the broker's newest policy as if it were the file's policy). Proved by `lib/mcp/tools/broker-book.test.ts` as a rule and by `npm run check:mcp` over HTTP on both shapes.

**Never delegated to an agent:** approving or rejecting a money-out, sending a claim payment, issuing a refund, binding a policy, cancelling a policy, voiding or correcting, running or publishing a broker statement, changing a KYB status, creating or revoking an API key, replaying a webhook or writing into the ledger directly. That list did not have to move when `explain_amount` and `list_my_activity` were added: both only read, they write nothing anywhere, and the surface still has exactly one tool that writes at all on a money path, the one that queues a request for a human. It did not have to move for `inspect_reference` either: the eighth tool only reads, and it refuses an MCP key prefix rather than making the line about API keys smaller. An agent principal is refused as an approver by the application and by a database trigger, and an agent-held key cannot be created for a `staff_approver` at all. Only a `staff_ops` user can create or revoke a key: an approver who could mint a key for the maker would be both halves of the maker-checker gate, raising a claim payment through that key and then approving it as themselves. A request raised through the MCP endpoint is marked as agent-raised on the approval queue so the human approver sees it before deciding. Transcript of a session against the local app: `docs/handoffs/b11-mcp-session.md`.

A rehearsed live demonstration for the debrief is written up in [docs/handoffs/b12-1-agent-demo.md](docs/handoffs/b12-1-agent-demo.md): the client configuration for the Claude Code CLI (`claude mcp add --transport http corgi-trial <deployed URL>/api/mcp --header "Authorization: Bearer <key>"`) and for the MCP Inspector, the prompts, the figures they return on the trial data, and the four independent reasons an agent cannot approve a money-out. The endpoint was exercised on the deployed application by a real MCP client on 2026-09-08 (MCP Inspector 2.5.0, protocol 2025-11-25): the five tools, then a $1,200.00 claim payment request that queued as agent-raised approval request `8148a717` and was rejected by a human approver 87 seconds later. Nothing moved: evidence in [docs/evidence/b12-1/](docs/evidence/b12-1/).

## Inbox

`/inbox` is the notification centre of the signed-in role: every waiting item on one page, grouped by screen, with the link that does the work (a policy to pay, an endorsement delta to pay, a correction difference to collect, a quote waiting for the customer, a change request to answer; an endorsement or a correction to approve for a customer; approval requests, policies paid and not bound, endorsements paid and not applied, claims with a payment to move, the open breaks and the statements the monthly close produced this month for staff; and, for a broker, the statement the monthly close produced for them). The sidebar counts and the "what needs you" block point at it. Every count is the length of the list it points at, read with the same readers the screens use, so a badge and its list cannot disagree.

## Operations console (staff only)

`/ops/console` is the cockpit of the trial system for `ops@example.com` and `approver@example.com`: a live feed of everything that happened (payments, refunds, webhooks, KYB, claims, approvals, MCP calls, statement runs, reconciliation runs), an errors panel (a failure, a refusal, or any provider operation accepted more than 15 minutes ago and still unconfirmed, shown as "checking" before that; the 15 minutes are an assumption of this build), five tiles with real p50 and p95 latencies over 24 hours, and a "what is waiting" block. The page refreshes itself every 10 seconds from the server and has a Refresh button; nothing on it is pushed. `/ops/console/search` finds any reference (a Stripe id, a policy number, a claim number, a key prefix, an email) and shows its trail. Four 360 pages (`customer`, `broker`, `policy`, `claim`) gather everything known about one subject. `/ops/console/infra` lists the free-plan limits of Vercel, Neon and Stripe with the measured usage next to the documented limit, each limit quoted from the provider page it links to. Every read is wrapped: a failing query prints one named red line and the rest of the page renders. Personal data is masked to its first three characters behind a fold that reveals it on click. The console reads only: its two buttons post to the existing reconciliation and KYB re-check routes, and the runtime role holds no UPDATE or DELETE. Review record: `docs/reviews/b13-9-console.md`.

## Activity log and structured logs

Every route handler under `app/api` (34 files), the cron job endpoints, the MCP endpoint and the Stripe webhook are wrapped in one helper, `withActivity` (`lib/observability/log.ts`). It gives the request a correlation id (the incoming `x-request-id` header when there is one, otherwise a uuid), times the handler, classifies the outcome, and writes the result in two places at once: one append-only row in `activity_log` (migration 0021) and one JSON line on stdout with the same fields and nothing else, so a line in the Vercel log and a row on the console screen are recognisably the same request. A request is `refused` when a rule said no (a 4xx, or a redirect carrying `?error=`, which is how most screens here say no), `error` when something broke, `ok` otherwise, and the status code stored is the one the caller actually received. The **rule** a refusal named comes from the route itself, which declares the gate it enforces; a request refused before that gate is reached reads `sign in` (no session) or names no rule at all (a malformed id), because a record that can never be corrected must not guess. The duration measures everything the wrapper adds up to the moment the answer is ready, the row insert excepted, which happens after. The row never breaks the request: if the insert fails the JSON line is still printed and the handler's answer is returned unchanged, and the two timestamps differ by design (the line carries the application clock, the row the database clock; the correlation id is the join key).

**No payload is ever stored, and the table has no column for one.** The only free text is one sanitised sentence produced by `lib/observability/redact.ts`: emails are masked to their first three characters, a bearer token, a password field, a connection-string password and any `sk_`, `rk_` or `whsec_` secret are replaced, newlines are collapsed and the length is capped. Stripe and MCP references (`pi_`, `cs_`, `re_`, `acct_`, `cmk_`) stay readable because they identify things and authenticate nothing. A stack trace is never read: only `error.message` reaches a log line. The password field of the sign-in form is never seen by the wrapper, which records that route as anonymous by construction.

`activity_log` carries the guards of the money tables even though it holds no money: UPDATE, DELETE and TRUNCATE are refused for every role including the owner, the recording time comes from the database clock, and `app_runtime` holds SELECT and INSERT only. The reason is the one `mcp_calls` has: it records what was refused and by which rule, and a refusal that can be rewritten is not a record. `npm run check:money-guards` proves it on the same list as the money tables.

The console reads it. `/ops/console` gains **Refused and failed actions** (newest first, bounded, with the rule and the sanitised sentence, actors masked like the rest of the console) and **Latency by route** (p50, p95, max, request count and refusal count per route over 24 hours, computed by Postgres). The four 360 pages gain an **Activity** panel of the requests about that object. `/ops/console/search` resolves a correlation id and leads to the object the request named.

## Customer change requests

A customer signed in on `customer@example.com` opens their own policy at `/policies/{id}` and reads it: the terms in force, the endorsement schedule, the documents as of any date and the timeline. No journal, no ledger sums, no action but one, "Request a change": they tick the lines the request is about (insured name, mailing address, per-occurrence limit, aggregate limit, annual premium, effective date, other) and write a comment. The owning broker sees it on the same policy page, above the endorsement schedule, and as "N change requests to answer" in "what needs you"; they answer it once, either with an answer or by saying the change has been made.

A change request moves no money and changes no policy: the change itself goes through the normal endorsement flow, which prices it, collects the delta and writes the policy event. Both tables (migration 0019) are append-only with the same guards as the money tables: a broker cannot rewrite what a customer asked, a customer cannot rewrite a request after the answer, and a request has exactly one answer because the database says so. Billing model of this build: agency bill, the broker starts the Stripe payment on the customer's behalf; the customer decides (approvals above $500) and never acts on money.

## Money rules of this build (decided by the candidate, see DECISIONS.md)

USD integer cents everywhere. A term is one calendar year (February 29 to February 28); premium earns pro-rata daily over the real day count. Endorsement deltas are priced over the remaining days from the effective date, never the entry date. The insurer eats the rounding penny: charges are rounded down, refunds rounded up. State premium tax: California, 2.35 percent (Cal. Const. art. XIII s. 28(d)), refunded pro-rata with the premium and capped at the tax charged; the $25 flat policy fee is an assumption of this build, fully earned at issuance, never refunded. Commission is earned on collected premium, clawed back on refunded premium, rounded down. Cancellation is pro-rata; short-rate is representable (method stored on the event, penalty account exists) but not computed. Money-out above $1,000 needs a distinct human approver (assumption, not a Corgi rule). Money that arrives for a broker who lost eligibility between the payment page and the payment is journaled at once in a suspense account (unapplied customer cash) and applied to the policy when staff bind it, so ledger cash equals Stripe cash at every instant. Known gap of v0: refunding that parked money to a customer whose broker fails for good is not built; the balance stays visible in the suspense account and on the reconciliation screen until it is applied or refunded by hand in the Stripe sandbox (which the reconciliation would then show as provider-only until recorded). A claim payment counts as paid when it is sent on the rail (incurred = paid + reserve stays two terms); cash leaves the rail account only at settlement, shown separately, and a bank return undoes the payment. The $1,000 approval threshold is cumulative per claim: a payment that alone or together with what the claim already sent or has waiting exceeds $1,000 needs a distinct approver.

Recited example: $1,200 written March 1, 2028 (365 days), tax $28.20, fee $25, charge $1,253.20; cancelled June 9, 2028: earned 32876 cents, unearned 87124, tax refunded 2048, fee 0, total refund $891.72, clawback 13068 cents.

Rule 21 (decided 2026-09-08): a claim payment requested through the MCP endpoint by an agent principal always creates an approval request, whatever the amount; the $1,000 threshold applies to people. The claim screen and the approvals queue both say "raised by an agent" with the key prefix, and an agent-raised payment without a request never leaves (the send gate fails closed).

## Explain this amount

Every money figure on the screens carries a fold saying how it was produced: the formula in integer cents, the days and the rate where they apply, the rounding rule by name, and the journal entries (type, effective date, recorded time) that prove it. It is server-rendered from the same pure functions the ledger posted with (`lib/money/explain.ts`): the endorsement and correction folds reuse the formula lines stored on their events, a fold over a sum of journal lines calls the same function the figure was computed with, and the component checks on every render that the explanation ends on the figure above it, printing an alert instead of hiding a disagreement. The endorsement fold replays stored figures, so that comparison would be a figure against itself: it carries a second check instead, which prices the endorsement again on the server from the inputs stored on its own event and prints "Recomputed today from the same inputs: identical" or names the figure that disagrees (review finding F-INT-05). Twenty-three figures are covered: the policy's terms in force, each endorsement's prorated delta, the seven cancellation amounts, the four ledger sums, a claim's paid, reserve and incurred, and the five broker statement totals. Nothing is computed in the browser.

The policy page's "as it stood on a date" panel offers the dates that matter as links carrying `?asOf=YYYY-MM-DD`: the term start, every effective date still in force, and today. A change a correction put right is not offered, because the fold no longer applies it. Each click is a fresh server render, so the address can be bookmarked or sent to somebody else, and the declarations and schedule PDFs follow the same date.

Statements carry a format version (1, 2, 3): a revision keeps the version it was written under, and two revisions of different versions read "format changed, not comparable by hash" instead of identical or changed (migrations 0016 and 0020).

Statements are also produced on their own. On the first day of a month (UTC) the daily cron job runs the monthly close after reconciliation (`lib/statements/monthly-job.ts`): for every broker with a journal movement in the month that just ended, or a policy in force, it calls the same `runStatement` a staff member calls, with no author and with the knowledge cutoff set to the instant it ran. It runs once: before publishing a broker it looks for a run of that broker and that month whose cutoff is at or after the end of the month, so a second call the same day, a retried cron or a manual replay produces nothing, while a provisional run somebody made during the month does not block the definitive one (it becomes the revision it supersedes). Each statement produced leaves one `activity_log` row under the correlation id of the job, and the job summary carries the month, how many were produced, how many were already published and any broker the run was refused for. Staff see them in the inbox as "Statements produced this month", a broker sees "Your statement for <month> is ready"; `npm run check:statements` proves the whole of it on the disposable database, including that a mid-month call produces nothing.

## Corrections and history

Nothing financial is ever updated or deleted: Postgres triggers refuse UPDATE, DELETE and TRUNCATE on every money table for every role, the runtime role only has SELECT and INSERT, entries are sealed at commit, and the balance of each entry is checked by the database at commit. Corrections are reversal entries linked to the originals plus a dated policy event; the fold of policy events skips superseded events. Every entry carries an effective date (business time) and a recorded time (set by the database), so "as it stood on May 3" and "what was known on May 3" are two different queries over the same rows.

Known facts about the demo data: policy CGP-01061 was bound during development on a locally signed webhook, then corrected by reversal (the reversal entries and the correction event are visible on it; its Checkout Session was expired at Stripe). Two synthetic replay-test events (`evt_replaytest_*`) and a few probe payments with metadata `corgi_probe` exist in the Stripe sandbox and the inbox; they are stored, marked ignored, and never posted. The refund of CGP-01062 ($3,241.56) was issued before maker-checker existed and therefore had no approver; that gap is disclosed here and closed by the approvals slice.

## Cut list v0 and week-two plan

Deliberately not built: renewals, a public REST API (MCP is the machine surface), a customer portal beyond approvals and documents, ACH collection, installment billing, e-signature, USDC payout, a second product line, reinsurance, broker API keys. Production-only work recorded as limitations rather than built: a real KYB policy, real tax filings, real bank rails, Stripe fee accounting, revocable sessions. Week two, in order: a dedicated KYB vendor behind the same interface, ACH collection, Plaid bank verification and Increase payout rail live, renewals, installment billing, then the public API.

Parked money (decision 27): money received after a broker lost eligibility sits in the suspense account unapplied_customer_cash (rule 14; example: 125320 cents received while the Checkout page was open). Returning it is a money-out that would need the approval queue, and this build offers no refund action for that account; the balance is visible on the ledger and disclosed here rather than hidden.

Week-two items decided on day 2: a database trigger refusing an approval decision by the person who created the MCP key through which the request was raised (decision 26; this build closes the path by letting only staff operations create or revoke keys), and a guard on the rate tables (brokers.commission_rate_bps, state_tax_rates), which are safe today because every rate is frozen on the event that used it.

Reconciliation note: the open breaks on the deployed application were sandbox probe payments left by the checks and reviews that created them, and there is deliberately no button to dismiss a break: nothing on these screens edits or deletes a reconciliation row. A real break would therefore arrive as one more line among them, so read the reference and the age rather than the length of the list. The board separates the two: a probe is classified as a probe and listed apart from the breaks to act on. A **probe** is a payment this project's own check script creates: every run of `npm run check:reconciliation` puts one real PaymentIntent of $42.42 into the Stripe sandbox, with a test card, no operation id and the metadata `probe=check-reconciliation`, to prove that money at the provider with nothing behind it in our books is found. No ledger entry will ever explain them, so the classifier gives them their own sixth classification (the ones planted before the marker existed are recognised by that amount and their `corgi_probe:` description); they are listed under "Probe payments from check runs", counted separately on the run summary, and left out of the breaks to act on and of the operations inbox. **Explaining** a break is the other half: a staff operations user writes a note of 10 to 500 characters on a break, and it moves to "Explained breaks" with the note, its author and its date, out of the count and out of the inbox. A note is append-only (`reconciliation_break_notes`, migration 0022, same guards as the money tables) and **nothing here repairs money**: no journal entry is posted, no reconciliation row is edited or deleted, and every later run compares that break again exactly as before. A note explains **the break as the latest run described it**: the classification and the two amounts of that report are recorded on the note (migration 0025), because a break key deliberately survives a classification change. So a later run that reports the same break differently matches no note, and the break returns to the count, the operations inbox and the MCP tool, with the superseded note and its author shown beside it. The daily job keeps a break in its window for as long as no covering run has re-examined it, probes and explained breaks included, because that later run is what reports the break differently in the first place.
